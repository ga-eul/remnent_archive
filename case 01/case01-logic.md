# CASE 01 「신입사원」 게임 구조·규칙·상태값

이 문서는 현재 확정 상태만 담는다. 변경 이력과 근거는 `decisions.md`에 있다.
화면에 나오는 대사·메신저·엔딩 문구 원문은 `dialogue.md`에 있다.

---

## 1. 확정 원칙

- 고정 장소 5곳: **기록보관실 / 관제실 / 생활공간 / 업무실험실 / 제한구역**. 면담실 등 새 물리 장소를 만들지 않는다.
- 자동 페이지 전환 금지. ‘면담 시작’, ‘2차 조사 시작’, ‘최종 추론’ 모두 플레이어가 직접 누른다.
- 목표 플레이 시간 약 25~35분 (면담 1인당 3분 이내).
- 플레이어 표시 자료 13묶음 + 시스템 자동 생성 06-G. 05-B는 하위 레코드 2개(VHS·PERSONNEL)로 추적.
- 모든 추론 연결은 증거 보관함에서 플레이어가 직접 조합한다. 단서 획득(clue)과 조합 추론(connection)은 **별도 상태값**이다.
- 정답을 한 문서에서 바로 알려주지 않고, 서로 다른 증거를 조합했을 때 새로운 사실을 추론하게 한다.
- 시스템은 정답을 알려주는 장치가 아니라 플레이어가 스스로 연결했다고 느끼게 하는 장치다.
- **단서는 직접 말하지 않고, 추리 결과에서 확인한다 (사용자 확정 D16)**: 개별 자료는 이상함·흔적만 보여 주고 결론을 말하지 않는다. 결론은 플레이어가 조합에 성공한 뒤 추론 결과 화면이나 확인 대사로만 확인한다. 이 확인은 플레이어가 이미 도달한 정답에 대한 보상이며 새로운 비밀 공개가 아니다 (예: C07 성공 시 래미 대사 "아, 드디어 찾으셨네요. HUMAN-04.", 05-D 열람 후 C08 기록에 추가되는 전임자 = HUMAN-03 확인). 확인 시점은 플레이어가 보유한 증거에 맞춘다.

## 2. 플레이어 인식 변화 (신입사원 수정본)

① 돈을 벌러 평범한 회사에 입사 → ② 회사·직원의 이상한 점 발견 → ③ 기억 추출·이전 실험 흔적 → ④ HUMAN-01~03 기록 → ⑤ HUMAN-04라는 다음 단계 → ⑥ 자신의 계정·기록·행동이 HUMAN-04와 연결됨을 추리 → ⑦ "내가 HUMAN-04였구나" → ⑧ 회사와 자신의 관계를 선택.

**전임자 쪽 인식 단계 (사용자 확정 D15)**: 초반 "나는 신입사원이다." → 중반 "회사 기록에 이상한 부분이 있다." → 후반 "나 이전에도 이 회사에서 비슷한 실험이나 사건이 있었던 것 같다." → 추리 "그 기록에 등장하는 전임자와 CCTV 속 인물이 관련되어 있는 것 같다." → 강한 추리 "혹시 그 전임자가 HUMAN-03인가?" → C08 성공 시 "제4의 인물 = 삭제된 전임자" 기록 → 05-D(HUMAN-01~03 목록) 열람 후 같은 C08 기록에 "전임자 = HUMAN-03" 추가 확인. CASE 01은 **"누구인가"까지만** 밝힌다. 왜 존재했는가 / 무엇을 당했는가 / 회사가 왜 그렇게 했는가는 다음 CASE로 넘긴다.

## 7. 증거 보관함 (화면 이름: My Archive)

- My Archive는 **획득한 단서 열람 + 단서 조합 시스템**이다 (D23). 목록은 [전체] / [문서] / [CCTV] / [단서 조합] (D40). CCTV = 03-B, 05-B-VHS, 나머지는 문서. [단서 조합]에는 NEW 카드만. 화면 구성은 `prd.md` 4-2.

- 상단 수치: 획득 자료 n (총량 숨김) / 연결 성공 n / 현재 단계. 연결 성공 n은 일반 조합 8개(NEW 카드)의 성공 수이며 C13은 포함하지 않는다(D31).
- 획득한 자료만 표시. 미획득 자료·총량·결론이 담긴 표시명 금지. 언제든 재열람(최종 추론 이후에도). 사이드바의 자료 카드를 누르면 자료 창으로 다시 본다 (D39).
- 연결: 두 자료를 단서 조합 영역에 드래그앤드롭(모바일 탭)하고 [조합하기]를 누른다. 순서 무관. 두 단서를 모두 획득해야 조합 가능.
- 정답: 일반 조합 8개(C01·C04·C05·C06·C07·C08·C10·C11)의 결과가 **NEW 카드**로 My Archive에 추가되고 ‘새로운 단서 해금’을 표시한다. 카드 내용은 6절 추론 결과 문장, 카드 이름은 6절 NEW 카드 이름 표(R-32). C13은 일반 NEW 카드로 다루지 않는다(6절). NEW 카드는 [전체]·[단서 조합] 목록에 들어가며(D40), 다시 조합 재료로 쓰지 않는다. 누르면 조합한 두 자료와 추론 결과 문장을 보여 준다. C08 카드는 05-D 열람 시 내용이 갱신된다(D17).
- 오답: ‘연관성을 찾을 수 없습니다’, 시도 조합 회색 처리, 패널티 없음, 새 단서 생성 없음.
- 시도 횟수 (D26): 조합 횟수에는 총량 제한을 두지 않는다. 단 같은 두 자료의 조합은 한 번만 시도할 수 있다(정답·오답 모두, 순서 무관). 시도한 조합은 tried_pairs에 기록하고, 같은 조합을 다시 놓으면 조합할 수 없다. 성공으로 생긴 NEW 카드는 다시 조합 재료로 쓰지 않는다.
- 최종 추론 확인 시 연결 기능 전체 잠금 (예외: C13 연결 단계).
- 추리 메모장 (D46): My Archive에서 여는 플레이어 개인 메모장. 입력·수정할 수 있고 상태값 `memo`에 저장한다. 조사 단계 이동과 관계없이 유지된다. 게임 판정에는 쓰지 않는다.
- 래미의 관찰: 연결 시도·오답·열람 순서를 tried_pairs와 열람 기록으로 저장 (세계관상 래미가 수집하는 HUMAN-04 데이터). 06-D/E 로그에 일부 노출 가능. tried_pairs는 이 관찰 기록이면서 같은 조합 재시도를 막는 판정 기준이다(D26).

**C13 최종 추론 모드 (D28)**: C13 연결 단계의 화면 구성.
- 화면: 별도 페이지를 만들지 않고 My Archive 조합 화면을 **최종 추론 모드**로 바꾼다. 상단 라벨만 `최종 추론`으로 바꾸고, 06-G를 조합 칸 한쪽에 고정한다. 다른 칸에 플레이어가 후보 자료 하나를 넣고 [대조하기]를 누른다.
- 안내 문구: 넣지 않는다. 06-G 추가 시 ‘새로운 자료 추가’ 표시만 띄우고, 힌트 문구 없이 화면 구성으로 다음 행동을 알게 한다.
- 후보 범위: C13 진입 시점까지 플레이어가 획득한 **원자료 전체**. 제외: 06-G 자신, NEW 카드(C01~C11 결과), C13 결과, 미획득 자료. 개발자가 후보를 따로 고르지 않는다. NEW 카드는 후보 영역에서만 숨긴다(회색 처리하지 않음, D29). 일반 My Archive에서는 NEW 카드가 그대로 보인다. 후보 영역의 회색 카드는 "이미 대조한 후보"라는 뜻 하나뿐이다.
- 후보 수: 획득한 원자료 수에 따라 플레이어마다 달라진다. 후보 총수는 화면에 표시하지 않는다(R-30).
- 표시: 기존 My Archive 카드와 표시명을 그대로 쓴다(출처·기록 유형 중심, R-32). 단서 ID를 강조하지 않는다. 탭은 [전체]/[문서]/[CCTV] 유지, 새 카테고리 없음. 정렬은 획득 순서. 06-D/E를 포함해 어떤 후보도 강조하지 않는다.
- 오답: ‘연관성을 찾을 수 없습니다’(R-37), 패널티 없음, tried_pairs에 기록. 틀린 후보 카드는 목록에서 빼지 않고 회색 처리 + 재선택 불가. 실패 횟수 표시·새 실패 메시지는 없다. 첫 오답으로 C13을 실패 처리하지 않고, 다른 후보는 계속 대조할 수 있다(R-37a·D27).
- 정답: 06-D/E + 06-G → connection_C13 = true, C13 결과를 화면에 표시한다. 성공 순간 조합 영역을 잠근다(D29): 후보 선택·[대조하기] 불가, 성공 전 오답 카드 상태는 그대로, 결과 화면 유지, [최종 선택으로 진행]만 활성. 자동으로 넘어가지 않고 플레이어가 [최종 선택으로 진행]을 누른다(R-03). 결과는 My Archive에 저장하지 않고, 상단 "연결 성공 n"에도 넣지 않는다(D31). C13 성공 여부는 ‘대조 완료’ 표시와 connection_C13으로만 관리한다. 화면에는 성공 표시 ‘대조 완료’와 결과 문장 "계정은 존재한다. 그러나 해당 계정을 정상적인 직원으로 확인할 수 있는 인사 기록은 존재하지 않는다."를 띄운다(원문 `dialogue.md` 6절, D30). ‘대조 완료’는 일시 메시지가 아니라 결과 문장 위에 계속 남는 상태 표시이며, ‘대조 완료’ + 결과 문장 + [최종 선택으로 진행]은 다음 단계로 넘어갈 때까지 유지되고 새로고침·불러오기 시에도 함께 복원된다(R-80). 결과 문장은 의미를 고정하고 표현은 톤 통일을 위해 다듬을 수 있다. HUMAN-04·실험 대상이라는 말은 넣지 않는다. C13은 시스템이 정체를 설명하는 단계가 아니라, 플레이어가 계정과 직원 신원 기록의 불일치를 최종 확정하는 단계다.
- 엔딩 3: disconnect_eligible = C04 && C08 && C10 && C11 && C13, [최종 선택으로 진행] → 확인 창 [진행]을 누를 때 판정. C13 미성공이면 [회사와의 연결을 차단한다] 비활성 + ‘연결을 차단할 근거가 부족합니다’.
- [최종 선택으로 진행] 확인 창 (D29): 버튼을 누르면 바로 넘어가지 않고 확인 창을 띄운다(문구 `dialogue.md` 6절). C13 성공·오답 후·미시도 어느 상태든 **같은 문구로 항상** 띄우며, 상태별로 문구를 바꾸지 않는다(C13 진행 여부를 알려 주는 힌트가 되지 않게). [진행] → 엔딩 3 자격 판정 후 최종 선택지. [취소] → C13 최종 추론 모드에 그대로 남는다(조합 영역·오답 카드·성공 상태 유지). C13 미시도 상태에서도 [진행]으로 넘어갈 수 있다.
- 06-G 본문 작성 원칙: 06-G는 "계정은 존재하지만 그 계정의 신원을 명확히 확인할 수 없다" 수준의 정보만 준다. ‘인사 기록 미등록’·‘TEMP’ 같은 06-D/E의 표기나 "06-D/E를 확인하라"는 지시를 06-G에 넣지 않는다. 06-D/E에는 인사 기록상 정상 직원 등록이 확인되지 않는다는 정보가 있어서, 두 자료를 직접 비교해야 "계정은 있는데 사람으로서의 신원 기록은 없다"는 모순에 도달한다. 06-G가 06-D/E를 가리키는 구조가 아니라, 두 자료가 서로를 보완해야 결론이 나는 구조로 쓴다.

엔딩 판정은 자동 우선순위가 아니라 **선택지 자격**으로 적용한다: 엔딩 3 조건 충족 → 차단 선택지 활성 / 엔딩 2 조건 충족 → 선택지 표시 / 둘 다 아니면 엔딩 1. 엔딩 2·3은 모두 "정체를 밝혀낸 플레이어"가 전제이고, 엔딩 1은 정체 추리 실패 루트다.

**ENDING 01 연출**: 채용 평가처럼 시작 → 5개 데이터 항목이 하나씩 ‘수집 완료’ → HUMAN-04 등장 → 완성도 등급 → 결과 화면 직후 자동 로그아웃 → 공동 연출. 의미: 회사가 얻은 것은 기억이 아니라 인간이 스스로 선택하고 판단하는 과정이었다. (엔딩 1 문구에 ‘기억 보존’ 표현 금지)

**ENDING 02 연출**: 이전 진행률 0→100% → 기존 계정 DEACTIVATED → 같은 이름의 새 자아 데이터 모델 계정 생성 → 완성도 등급 → 공동 연출. 원본 인간의 이후는 공개하지 않는다. 의미: 보존된 것은 플레이어가 아니라 플레이어를 재현하는 데이터 모델. 구원인가, 자신을 잃는 선택인가.

**ENDING 03 연출**: 연결 차단 진행 화면에서 C가 남긴 기록(보안 담당 확인 메모)이 열림 → 연결 차단 진행 → 이름이 NULL로 → 인트라넷 사용자 목록에서 사원번호 DA-A와 이름 삭제 → 인트라넷 글리치 → 완성도 등급 → 공동 연출. 데이터가 완전히 파괴됐는지는 확정하지 않는다. 의미: 회사는 기억을 수집할 수는 있어도, 플레이어가 자신을 누구라고 생각하는지까지 통제할 수는 없다. C의 메모는 엔딩 3 연출 화면 안에서만 표시하며, 메신저 위젯에는 표시하지 않는다.

- R-82 엔딩을 본 뒤 새로고침하면 엔딩 수집 화면으로 이동.
- R-83 엔딩 수집 화면(허브의 [보존 기록]과 같은 화면)은 본 엔딩과 최고 등급만 공개, 보지 않은 엔딩은 번호(‘ENDING 02’ 등)와 자물쇠 아이콘만 표시하고 제목·내용·등급은 보여 주지 않는다 (D42). 엔딩 수집 뒤에는 허브로 돌아가며, [유출된 기억]이 열려 있으면 그 화면의 PRESENT · CASE 01 카드로 돌아간다. ‘처음부터 다시’는 허브의 [입사 지원하기]와 PRESENT · CASE 01 카드 안에 둔다.
- R-84 CASE 01 status가 `in_progress`일 때 [입사 지원하기] 또는 ‘처음부터 다시’를 누르면 확인 창을 띄운다(문구는 `dialogue.md` 5절). [처음부터]를 고르면 `remnant.present-01`만 비우고 새로 시작한다. `remnant.global`(본 엔딩·등급·설정)은 지우지 않는다.
- R-85 CASE 01 status가 `finished`이고 중간 세이브도 없으면 허브의 [이어서 출근하기]는 비활성이 되고 보조 문구 ‘근무 종료’를 표시한다 (D43). `none`이면 비활성 + ‘기록 없음’. 다음 플레이는 [입사 지원하기]로 새로 시작하고, 엔딩 기록은 [보존 기록]에서 본다.

- R-86 [최종 추론 시작]을 누르면 최종 추론 직전(3차 수색) 상태를 중간 세이브로 남긴다(최대 3개, `remnant.present-01.saves`). 허브 [이어서 출근하기]는 진행 중 기록과 중간 세이브를 파일 카드(테마 이름·지점·저장 날짜)로 보여 주고, 중간 세이브를 고르면 그 상태로 불러와 status를 in_progress로 바꾼다. 허브는 `remnant.global`의 요약(`progress`·`saves`)만 읽는다 (D43).

## 15. 날짜·시간 설정 규칙

**표기 형식 (사용자 확정 D23)**: 게임 내 기준 날짜는 4XXX년 4월 12일(목). 시각이 필요한 기록은 `4XXX.04.12 09:17` 형태로 쓴다. 아래 15.2~15.9의 날짜 예시(10월 17일 등)는 정밀도 설명용이다.

단서·기록에 들어가는 날짜·시간의 정밀도 기준. 새 날짜·시간을 정하거나 바꿀 때 이 절을 먼저 확인한다.

### 15.1 기본 원칙

「신입사원」의 단서와 기록에 들어가는 날짜·시간은 **모든 정보를 세세하게 확정하지 않는다.**

이 게임의 핵심 추리는 날짜 자체를 맞히는 것이 아니라,

> **기록 간 불일치 → 사건의 관계 파악 → 기존 단서의 재해석 → 진실 추론**

이므로, 날짜와 시간이 실제 추리에 필요하지 않다면 `X월 X일`, `X월 중순`, `최근`, `정기점검 당시`, `사건 전후`처럼 뭉개서 표현한다.

세부 날짜를 너무 일찍 확정하면 CCTV, 출입기록, 업무기록, 복구영상, 시스템 로그 등의 시간관계가 불필요하게 복잡해지고 이후 스토리 수정 시 연쇄적으로 설정이 꼬일 수 있다.

### 15.2 날짜를 정확하게 설정해야 하는 경우

다음 조건에 해당할 때만 정확한 날짜·시간을 확정한다.

#### 🔴 필수 정밀도

**날짜 또는 시간이 실제 추리의 핵심 단서가 되는 경우**

예:
- CCTV의 특정 시각과 출입기록이 일치하는지 비교해야 하는 경우
- 사건 전후 순서를 정확히 판단해야 하는 경우
- 특정 시간에만 발생한 시스템 오류를 추리해야 하는 경우
- 정기점검 시간과 CCTV 기록 공백이 직접 연결되는 경우
- 시스템 로그의 시간 차이가 인물의 행동을 증명하거나 반박하는 경우

이 경우에는 실제 날짜와 시간을 설정한다.

예:
```text
10월 17일 14:20
```

### 15.3 대략적인 시점만 필요한 경우

날짜의 정확한 값보다 **사건의 선후관계**만 중요하다면 정확한 날짜를 만들지 않는다.

사용 가능한 표현:

- X월 중순
- X월 하순
- 정기점검 기간
- 정기점검 당시
- 사건 전
- 사건 직후
- 사건 이후
- 최근
- 며칠 전
- 지난주
- 이전 기록
- 입사 초기
- 해당 기간

예:

```text
10월 중순
정기 보안점검 실시
```

또는

```text
정기점검 직전
C가 기록보관실 방향으로 이동
```

이 정도로 충분하다.

### 15.4 날짜가 추리에 필요하지 않은 경우

단순한 배경 정보나 분위기를 위한 기록에는 구체적인 날짜를 넣지 않는다.

예:

```text
최근 회사에서 이상한 일이 계속 생기는 것 같다.
```

생활공간 일기나 일반적인 업무 대화 등에 날짜가 반드시 필요하지 않다면 `최근`, `요즘`, `며칠 전` 등의 표현을 사용한다.

### 15.5 정기점검 일정 설정 규칙

정기점검은 **추리 장치인지 단순 배경인지**에 따라 날짜 정밀도를 결정한다.

#### 정기점검이 단순 배경인 경우

정확한 날짜·시간을 설정하지 않는다.

예:

```text
정기 보안점검
월 1회 실시
시스템 및 출입기록 점검
```

또는:

```text
최근 정기점검 기간
```

#### 정기점검이 추리 장치인 경우

정확한 시간대를 설정한다.

예:

```text
10월 17일 14:00~15:00
정기 보안점검 실시
```

그리고 이 시간대가 CCTV 공백, 출입기록, 시스템 로그 등과 직접 연결되도록 설계한다.

핵심 기준:

> **정기점검 = 배경 설정 → 날짜 정밀도 낮게**
>
> **정기점검 = 추리 장치 → 날짜·시간 정밀하게**

### 15.6 「신입사원」의 날짜 정밀도 3단계

모든 기록에 같은 수준의 날짜를 적용하지 않는다.

| 중요도 | 정밀도 | 표현 예시 | 사용 목적 |
|---|---|---|---|
| 🔴 필수 | 정확한 날짜·시간 | `10월 17일 14:20` | 시간 추리 |
| 🟡 관계 필요 | 대략적인 시점 | `10월 중순`, `정기점검 당시` | 사건 순서·관계 |
| 🟢 불필요 | 날짜 생략/상대적 표현 | `최근`, `이전 기록` | 분위기·배경 |

### 15.7 현재 주요 단서의 권장 날짜 정밀도

| 단서 | 권장 정밀도 | 이유 |
|---|---|---|
| 03-A 직원 명부 및 업무 기록 | 🟡 | 업무의 시점 관계는 필요하지만 모든 기록을 정확하게 할 필요는 없음 |
| 03-B CCTV 기록 | 🔴 또는 🟡 | 다른 기록과 시간관계를 추리할 경우 정확한 시간 필요 |
| 03-C 생활공간 일기 | 🟢~🟡 | 대부분 분위기·기억 정보이며 정확한 날짜가 핵심은 아님 |
| 04-A 직원 면담 종합 기록 | 🟢 | 면담 내용 자체가 핵심이며 세부 날짜는 중요하지 않음 |
| 05-A 인간과 기계의 업무 비교 | 🟢 | 비교·연구 내용이 핵심 |
| 05-B-VHS 복구된 영상 기록 | 🟡~🔴 | 영상의 시점이 다른 기록과 연결될 경우 정확도 필요 |
| 05-C 기억 추출 실험 기록 | 🟡 | 실험의 진행 순서와 이전 기록과의 관계가 중요 |
| 05-D 이전 실험 참가자 자료 | 🟢~🟡 | 실험 순서가 중요하고 정확한 날짜는 대부분 불필요 |
| 05-E 보안 시스템 예외 접근 기록 | 🟡 | 우회 행동이 어느 시점에 발생했는지 정도의 관계가 중요 |
| 06-A HUMAN-04 통합 실험 보고서 | 🟢 | 현재 실험의 내용과 의미가 핵심 |
| 06-D/E 플레이어 계정 이력 및 시스템 감사 로그 | 🔴~🟡 | 계정·행동·기록의 시간관계가 추리에 사용될 수 있음 |
| 06-G 사용자 식별 실패 보고서 | 🔴 | 최종 확인 과정 및 시스템 상태와의 관계가 중요할 수 있음 |

※ 위 정밀도는 **현재의 기본 권장값**이며, 실제 추리 구조가 변경되면 필요한 부분만 상향 조정한다.

### 15.8 날짜와 시간보다 먼저 확정해야 하는 것

스토리 설계 단계에서는 정확한 날짜보다 **사건의 시간적 관계**를 먼저 확정한다.

예:

```text
사건 이전
↓
정기점검 예정
↓
사건 발생
↓
CCTV 이상 발생
↓
업무기록 생성
↓
기록 간 불일치 발견
↓
2차 조사
↓
복구영상 발견
↓
제한구역 조사
↓
최종 신원 확인
```

이 순서가 확정된 후 실제 날짜가 필요한 부분에만 날짜·시간을 부여한다.

### 15.9 개발 단계별 날짜 설정 방식

날짜·시간은 한 번에 완성하지 않고 3단계로 확정한다.

#### 1단계 — 스토리 설계

정확한 날짜를 만들지 않는다.

```text
X월 X일
사건 전후
정기점검 당시
최근
이전 기록
```

#### 2단계 — 추리 설계

단서 간 시간관계를 확정한다.

```text
A보다 B가 먼저 발생
CCTV 공백은 정기점검 시간과 겹침
출입기록은 CCTV보다 약 10분 뒤
```

이 단계에서도 실제 달력 날짜가 반드시 필요하지 않다면 확정하지 않는다.

#### 3단계 — 실제 구현

게임 화면에 표시할 필요가 있거나 추리에 필요한 부분만 정확한 날짜·시간으로 확정한다.

```text
10월 17일 14:20
10월 17일 14:30
10월 17일 15:05
```

### 15.10 금지해야 할 설계 방식

다음과 같이 **모든 단서에 무조건 정확한 날짜와 시간을 부여하지 않는다.**

잘못된 예:

```text
직원 명부: 10월 12일 09:12
CCTV: 10월 12일 09:17
업무기록: 10월 12일 09:23
생활공간 일기: 10월 11일 22:47
복구영상: 10월 13일 16:02
출입기록: 10월 12일 09:31
```

이렇게 만들 경우 실제 추리에 사용되지 않는 숫자까지 플레이어가 의미 있는 정보로 받아들일 가능성이 있다.

또한 개발 중 하나의 설정을 수정하면 여러 기록의 시간도 함께 수정해야 하므로 설정 유지보수 난도가 불필요하게 올라간다.

### 15.11 날짜는 '추리 가능한 정보'일 때만 단서로 취급한다

플레이어에게 날짜가 표시되었다고 해서 그 날짜 자체가 자동으로 추리 단서가 되는 것은 아니다.

다만 플레이어가 다음과 같은 관계를 발견할 수 있도록 의도적으로 설계했다면 날짜·시간은 중요한 단서가 된다.

```text
CCTV 시간
+
출입기록 시간
↓
인물의 이동 가능 여부 확인
```

또는:

```text
정기점검 시간
+
CCTV 기록 공백
+
출입기록
↓
특정 시간대의 이상 발견
```

이처럼 **두 개 이상의 기록을 시간으로 비교해야 할 때만 정확한 시간 설정을 사용한다.**

### 15.12 최종 원칙

「신입사원」의 날짜·시간 설정은 **디테일을 많이 만드는 것이 목적이 아니다.**

목적은 플레이어가 필요한 시간적 관계를 자연스럽게 추리하도록 만드는 것이다.

따라서 다음 원칙을 고정한다.

1. **날짜가 추리에 필요하지 않으면 세세하게 만들지 않는다.**
2. **사건의 선후관계가 중요하면 대략적인 시점으로 표현한다.**
3. **시간 자체가 추리의 핵심이면 정확한 날짜·시간을 확정한다.**
4. **CCTV, 출입기록, 시스템 로그처럼 서로 비교되는 기록은 필요한 경우에만 정밀하게 설정한다.**
5. **정기점검도 추리 장치가 아니라면 정확한 일정을 만들지 않는다.**
6. **스토리 단계에서는 시간관계만 먼저 확정하고 실제 날짜는 구현 단계에서 필요한 만큼만 부여한다.**
7. **모든 숫자와 날짜에 의미를 부여하지 않는다.**
8. **새로운 날짜 설정이 기존 단서·사건 순서·엔딩 조건과 충돌하지 않는지 확인한다.**

> **핵심 규칙:**
>
> **“정확한 날짜가 필요한 추리에는 정확하게, 필요하지 않은 정보는 의도적으로 뭉개서 설정한다.”**
>
> 「신입사원」은 시간 추리 게임이 아니라 **기록의 불일치와 관계를 추리하는 게임**이다.
